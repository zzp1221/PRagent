# step7 SPEC：证据位置范围校验，并划清语义校验的边界

## 背景

`docs/p0/INDEX.md` 记录的残留项是"证据门只保证引用真实存在且同源，不判断该工具输出是否
支持这条结论"。这一项一半可做、一半不可做，需要分开处理而不是一句"不做"。

## 仍然存在的确定性缺口（可做）

P0-4 让 `evidence_id` 必须在账本里存在，但没有校验**那次工具调用针对的是哪个文件**：

- `pragent/telemetry.py` 只记 `evidence_id -> tool`。
- 于是 `ast_analyze` 针对 `b.py` 的结果，可以被挂在 `a.py` 的发现上，仍然算强证据。
- 这类"跨文件借证据"是纯确定性问题：账本里就有工具参数，不需要模型判断。

## 不可做的部分（如实记录，不假装解决）

"这份工具输出是否支持该结论"要求理解语义。例如 `ast_analyze` 报告 `a.py` 有 `eval`
调用，而结论说的是"存在注入风险"：前者是事实，后者是推理。要判断推理是否成立，必须
让模型参与，那就不再是确定性门禁，也引入了额外调用成本与不可复现的输出。

本步不引入模型判定，只在报告里保留证据明细供人审阅。

## 目标

1. 账本除 `evidence_id -> tool` 外，再记录该次调用涉及的文件（如果工具有 path 参数）。
2. 门禁对"文件范围明确"的工具校验声明位置与实际调用位置一致，不一致则该引用不计入有效/强证据。
3. 对没有 path 参数的工具（全文检索、扫描器、符号查询）不做范围校验，避免误杀。
4. 计数进入 `gate.checks`，可观测。

## 范围工具集合

`read_file`、`ast_analyze`、`git_context`、`changed_line`、`locate_tests`：参数里有
明确的 path，语义上绑定单个文件。

其余工具不纳入：`search_repository` 与 `search_diff` 是全文查询，`symbol` 跨文件，
`run_scanners` 与 `run_repository_checks` 是整仓操作，`list_repository`、
`read_project_controls` 返回多文件。

## 约束

- 路径比较做规范化（反斜杠转正斜杠、去掉前缀 `./`），但不做大小写折叠，避免在大小写敏感
  文件系统上把两个不同文件当成一个。
- 账本缺位置信息时（旧检查点、无 path 参数）跳过校验，保持向后兼容。
