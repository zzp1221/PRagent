# step6 SPEC：结果写入的租约 fencing

## 现状证据

P0-2 引入了跨进程执行租约（`pragent/task_lease.py`），但它只解决"谁能进入 handler"，
没有约束"谁能写结果"：

- `pragent/store.py` 的 `succeed` / `fail` / `transition` / `cancel` 都不检查租约。
- 场景：进程 A 持锁执行，遭遇长时间停顿（GC、挂起、调度饥饿）超过租约期限；
  进程 B 因租约过期合法接管并完成写入；A 恢复后继续执行并成功写入，覆盖 B 的结果。
- 这正是 `docs/p0/INDEX.md` 记录的残留项，也是 P0-2 SPEC 里如实写明的缺口。

## 目标

1. 持有租约的执行者写入终态或中间状态时，数据库校验 `(lease_owner, lease_token)`。
2. 校验失败时不写入，并让执行者得知自己已失去所有权，停止后续写入。
3. fencing token 随每次 acquire 递增，因此"同一 owner 重新获取"也不会让旧执行者通过校验。
4. 不持租约的路径（同步 API 审查、测试）行为完全不变。

## 非目标

- 不做分布式事务：仍然假设单个数据库是唯一事实来源。
- 不改队列语义：重复投递仍由租约挡在入口。
- 不为"已失去锁的长任务"做结果比对或人工合并；它的结果直接丢弃。

## 设计决策

**fence 是可选参数**：`fence=None` 时 SQL 不附加条件，保持同步路径与既有测试零改动。

**单条条件 UPDATE 判定**：与 acquire 一致，用 `rowcount` 判断是否真的写入，
避免"先查后写"的竞态。

**写入点返回布尔**：`succeed` / `fail` / `transition` / `cancel` 由返回 `None` 改为
返回 `bool`。调用方此前都忽略返回值，因此是兼容扩展。

**失去所有权用专用异常**：`LeaseLost` 由 `harness` 在成功写入被拒时抛出，
`service` 捕获后只记指标并正常返回，把任务交给当前持锁者，不触发无意义的重试。

**fail 分支不因 fencing 再抛异常**：失败路径已经在处理原始异常，若因失去锁而抛新异常会
掩盖真实原因，因此只返回 False。

## 残留边界（不解决）

fencing 保护的是**本数据库写入**。执行者在失去锁之后仍可能产生外部副作用（调用模型、
发 GitHub 评论）。若要彻底消除，需要把 token 校验推进到每一步外部调用之前；本步只保证
任务状态与报告不被过期执行者覆盖，这一点在下面如实记录。
