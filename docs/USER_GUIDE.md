# PRAgent 使用手册

这份手册面向使用控制台的人，而不是改代码的人。它按"我要做什么"组织：从启动服务、跑第一次审查，到读懂一份报告、提交反馈、把审查接进 GitHub。需要自己部署或改配置时，看仓库根目录的 [README](../README.md)。

控制台里每一页都做同一件事：把一次审查变成可以看懂、可以追问的结果。左栏是入口，页面顶部的按钮是当前页能做的事。

## 五分钟上手

先把服务跑起来。项目需要 Python 3.11：

```powershell
python -m pip install -r requirements.txt
python -m pragent
```

浏览器打开 `http://127.0.0.1:8080/`。如果启用了登录（`PRAGENT_AUTH_REQUIRED=true`），会先弹出登录框，填管理员用户名、密码，以及可选的租户 ID；只有一个租户时留空即可。登录状态存在当前浏览器里，刷新不会掉，点右上角"退出登录"可以主动清除。

第一次进来会落在**运行总览**。这里显示四张统计卡、最近任务列表，以及两个通往能力与反馈的快捷入口。如果右上角状态显示"需要配置模型"，去 README 的模型配置章节配好 `PRAGENT_LLM_PROVIDER` 与 API Key，重启服务后再提交审查。

## 发起一次审查

点左栏**发起审查**。表单只有四项：

- **仓库地址**：填 `owner/repository`，例如 `demo/api`。它只用于标识与报告标题，不会去克隆仓库。
- **PR 编号**：可选。手动贴 diff 时留空即可，留空会显示为"手动审查"。
- **运行模式**：目前是"多智能体协作审查"（`agentic`），需要已配置模型。
- **Unified Diff**：要审查的代码变更本身。

diff 有两种给法。直接粘贴 `git diff` 的输出，或把 `.diff` / `.patch` 文件拖到输入区，也可以点"上传文件"选择。文件上限 512 KB，超过会提示拆分。输入区下方会实时显示行数与字符数，方便你知道提交了什么。

底部"后台运行，提交后可继续操作"默认勾选。保持勾选时，提交后立刻返回任务号，你可以去别的页面做别的事；取消勾选则等这次审查跑完再返回。

点"开始代码审查"。提交成功后，右侧结果卡会出现任务号，并提供跳到任务中心的入口。

一次正常审查的时间取决于 diff 大小与模型速度，通常几十秒到两分钟。想自己生成一份 diff：

```powershell
git diff main...feature-branch > change.diff
```

## 读懂报告

点左栏**任务中心**，左侧列出全部任务，每行显示仓库、PR 编号、状态和更新时间。选中一条，右侧出现任务报告。

报告顶部先给结论：仓库与 PR、风险等级、问题数量，以及一组执行数字——模型调用次数、工具调用次数、token 用量或成本、耗时。这些数字是"这次审查到底做了什么"的直接证据，不是装饰。

报告的顺序是刻意的：**先问题，后过程**。每条问题是一张卡片，包含：

- **严重性**：严重、高危、中危、低危。它来自 finding 的 `severity`。
- **位置**：`文件路径:行号`，指向新增代码里的具体一行。
- **说明**：这个问题为什么成立，涉及什么输入、状态或调用链。
- **证据**：模型或扫描器实际看到的代码片段。
- **修复建议**：建议怎么改，通常给到具体写法。
- **测试建议**：改完之后用什么用例验证。

再往下是可展开的"执行详情"，里面有预算与质量门禁两段。**预算**显示整次审查共享的 token、时间与调用次数上限，以及实际用量；耗尽时会直接标明耗尽原因。**质量门禁**显示每条结论是怎么通过校验的：

- 位置证据：结论指向的行能否在新增代码里对上。
- 强证据数：AST、扫描器或调用链这类硬证据的条数。
- 已验证引用 / 未验证引用：证据引用能否回溯到真实的工具调用。
- 门禁结论：通过，或被拦下几项。

如果所有候选结论都没通过门禁，报告不会告诉你"没发现问题"，而是列出每条被拦下的候选及其拦截原因。这两种情况必须能区分开——一份空的审查报告和一份干净的审查报告完全是两件事。看到被拦下的结论时，通常意味着证据不足：补测试、给更完整的 diff 上下文，再跑一次往往能救回来。

底部"原始响应 JSON"保留完整任务对象，排查问题时用。

## 处理任务

任务中心顶部可以按仓库名、PR 编号或任务号搜索，也可以按状态筛选：全部、进行中、已完成、失败、已取消。

报告右上角的按钮随任务状态变化：

- **取消任务**：任务还在跑时出现，提交取消请求，正在执行的步骤会停下。
- **恢复任务**：任务失败或被中断时出现，从最近一次 checkpoint 继续，不会从头再花一遍钱。
- **复制报告**：把当前任务的 Markdown 报告复制到剪贴板。
- **创建修复分支**：任务已完成且有可修复的结论时出现。它针对可确定安全的规则生成补丁，验证通过后提交到新的 `pragent/fix-pr-*` 分支，不会直接改你的源分支。

手机上左侧列表会折叠，选中任务后进入详情视图，左上角"返回任务列表"退回列表。

## 提交反馈

审查不可能永远对。看到误报、漏报或修复建议本身有问题，就在任务报告底部展开"提交审查反馈"。这一步不是走过场——反馈会进入演进实验室，成为下一轮改进的输入。

提交反馈时选类型：

- **误报**：报告里说了但实际不成立的问题。
- **漏报**：你发现了但报告没提的问题。选这类时需要补上规则 ID、文件路径和行号（都可以留空，但填了更有用）。
- **坏修复**：修复建议本身有问题，比如改坏了原有逻辑。

可以关联到某一条已有结论，也可以不关联。说明栏必填，写清判断依据、预期行为或修复造成的实际问题，最多 2000 字。

提交后会显示"已记录"，本任务下方出现反馈历史，状态先是"待评测"，进入评测流程后变为"已解决"。同一个任务的反馈会一直保留在这里。

## Skills

**Skills** 页回答一个问题：现在这套审查到底会检查什么。

顶部是智能体协作审查的能力卡，显示模型运行时是否就绪以及当前 Provider 与模型名。下面列出每一项代码检查能力，点开可以看到它负责的领域、使用条件与当前版本。

改动过 `skills/` 目录后，点"重新扫描"让新任务加载最新版本；已经在跑的任务不受影响。

## 演进实验室

**演进实验室**是把反馈变成改进的地方，流程刻意保守：先生成候选，再用同一组样本回放评测新旧两版，只有指标不倒退才允许生效。

页面顶部"评测准备情况"列出生成候选前必须满足的条件，例如可用样本数、留出集数量、最低提升幅度。条件不足时生成会被拒绝，并说明缺什么。

点"从反馈生成候选"，系统会从尚未解决的反馈里寻找可用于改进的信号。若当前反馈没有可用的改进依据，会直接告诉你，而不是造一个假候选。评测跑完后，右侧"本次评测结果"显示新旧版本在同一组样本上的对比与门禁结论。

下半部分是"反馈与评测记录"：待处理的反馈案例和最近几次评测的运行记录。可以回看某次改进为什么被采纳或拒绝。

需要手动提交候选提示词时，展开底部"手动提交候选提示词"，填写 Skill 名称与候选内容，跑同一套回放评测。这条路径适合你已经有一份明确想试的提示词改动。

## 接入 GitHub PR

控制台适合手动审查。要让 PR 事件自动触发审查，需要 Webhook 加一条公网转发——细节在 README 的 GitHub Webhook 章节，这里只说操作顺序：

1. 在服务端设置 `PRAGENT_GITHUB_WEBHOOK_SECRET`，需要回写评论时再设 `PRAGENT_GITHUB_TOKEN` 并把 `PRAGENT_AUTO_POST_REVIEW` 改为 `true`。
2. 跑一条隧道把公网地址转到本地。仓库自带 `tunnel-quick.ps1`，默认只把 `/webhooks/github` 与 `/health` 暴露出去，管理台不会被公开；要长期固定域名就用 `tunnel.ps1`。
3. 在 GitHub 仓库的 Settings → Webhooks 里填 `https://<公网域名>/webhooks/github`，Content type 选 `application/json`，Secret 与上面的环境变量一致，事件只勾 Pull requests。
4. 新建或重新打开一个 PR，或在 PR 上推一次提交。GitHub 的 Recent Deliveries 里看到 202，控制台任务中心出现对应任务，就算接通了。

之后每次 PR 的 `opened`、`reopened`、`synchronize` 都会创建一次审查任务。审查结果默认只留在控制台，只有打开 `PRAGENT_AUTO_POST_REVIEW` 才会回写 PR 评论。

## 命令行与 API

不想点界面时，接口等价。先登录拿 token：

```powershell
$session = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8080/v1/auth/login `
  -ContentType 'application/json' `
  -Body (@{username='admin'; password='<密码>'} | ConvertTo-Json)
$headers = @{Authorization="Bearer $($session.access_token)"}
```

提交审查并查询结果：

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8080/v1/reviews -Headers $headers `
  -ContentType 'application/json' `
  -Body (@{repository='demo/api'; pull_request=12; mode='agentic'; diff=(Get-Content change.diff -Raw)} | ConvertTo-Json)

Invoke-RestMethod -Headers $headers http://127.0.0.1:8080/v1/tasks/<task-id>
Invoke-WebRequest -Headers $headers http://127.0.0.1:8080/v1/tasks/<task-id>/report
```

完整端点表在 README 的 API 章节。取消、恢复、重新扫描 Skill、重放死信这类操作不需要请求体，空 body 直接调用即可。

## 常见问题

**提交后立刻报错说需要模型。** `agentic` 模式必须有可用模型。配好 `PRAGENT_LLM_PROVIDER` 与对应 API Key，重启服务。Skills 页顶部的能力卡会显示当前状态。

**报告里一条问题都没有。** 先看任务报告里的"被门禁拦下的结论"。如果那里有内容，说明模型给出了候选但证据不足；补充上下文或测试后重跑。如果两处都为空，这次 diff 确实没有新增行级别的问题——注意项目只审新增行，改一行上下文不会触发结论。

**任务卡在"执行中"。** 看执行详情里的预算段。token 或时间上限耗尽会中止任务并把原因写进任务错误，这时用"恢复任务"从 checkpoint 继续，并按 README 放宽 `PRAGENT_AGENT_REVIEW_TOKEN_BUDGET` 等服务端上限。

**返回 401。** token 过期（默认一小时）或服务重启后失效。退出登录再登一次。

**显示"服务已连接"但数据都是空。** 任务列表只显示当前租户的任务。确认登录时选的租户 ID 与创建任务时一致。

**审查慢得离谱。** 大 diff 会显著拉长每个角色的上下文，这是主要成本来源。把一次审查拆成几个更小的 diff，通常比调大预算更划算。

## 术语表

| 术语 | 含义 |
|---|---|
| Lead | 主 Agent，判定风险、分配任务、最终综合结论 |
| Worker | 领域 Agent，负责安全或正确性/可靠性方向的取证 |
| Critic | 盲审 Agent，挑战已有结论、给出反例 |
| Finding | 一条审查结论，含严重性、位置、证据、修复与测试建议 |
| 门禁（Gate） | 结论发布前的校验，检查格式、位置证据、证据引用与置信度 |
| Skill | 某个领域的审查协议包，由 Lead 按任务选择后注入 Worker |
| 返工 | 高风险任务中 Worker 的第二轮，最多一轮 |
| checkpoint | 执行状态快照，任务失败后可以从中继续 |
